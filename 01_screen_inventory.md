# Screen Inventory & Front-End Surface Analysis
**Project:** Shared Multi-Brand LMS & Admissions CRM (`TeluguAI.com` & `GenAI99.com`)  
**Scope:** Complete Reverse-Engineering of All Front-End Screens, Modals, Forms, and Data Actions  
**Target:** PostgreSQL 16+ Database Architecture  
**Document Code:** `/database/01_screen_inventory.md`

---

## 1. Overview & Architecture Summary

The frontend is implemented as a client-side state-machine SPA hosted on Next.js 16.4.0. While physical URL routing is anchored at root (`/`), the application exposes **6 distinct portals** and **42 functional screen components** (totaling **~75 interactive surfaces** when accounting for modals, multi-step wizards, and sub-tabs).

### Portals Breakdown
1. **Shared Portal (Common Auth & Base UI)**: Multi-brand entry point, session switcher, status indicators.
2. **Super Admin Portal**: Multi-tenant platform administration, RBAC, brand setup, WhatsApp integrations, platform API keys, audit logging.
3. **Branch Admin Portal**: Campus operations, course catalogue, batch scheduling, student & faculty directories, attendance rosters, invoicing, announcements.
4. **Admissions Counselor Portal**: CRM lead funnel, Kanban pipeline, course pitch guides, student enrolment wizard, tuition payment tracking.
5. **Academic Trainer Portal**: Cohort management, class timetable, live attendance marker, learning materials, assignment manager, code grading, quiz builder, student progress reports.
6. **Student Learner Portal**: Student dashboard, video curriculum, live lecture join/replays, assignments workspace, interactive quizzes, attendance records, fee ledger & receipts, verifiable certificates.

## 3. UI-Implied Actions & Data Mutations Summary

| Action Domain | Frontend Triggers | Database Operations Required | Constraints & Side Effects |
|---|---|---|---|
| **Auth & Security** | Common login, role switch, brand switch, session timeout | `SELECT` on `users`, verify password hash, `INSERT` into `audit_logs` | Cross-brand role mapping via `user_roles`; session token creation. |
| **Lead Management** | Add Lead modal, move Kanban card, log disposition | `INSERT`/`UPDATE` on `leads`, `INSERT` into `lead_stage_history` | Deduplication on normalized phone/email per brand; timestamping stage changes. |
| **Student Enrolment** | Enrolment desk 4-step submit | `INSERT` into `students`, `enrolments`, `invoices`, `payments`; `INSERT` into `whatsapp_messages` | Atomic transaction: student provisioning + batch assignment + fee invoice + welcome message. |
| **Academic Scheduling** | Create batch, schedule live session | `INSERT` into `batches`, `class_sessions` | Exclusion constraint on `class_sessions` to prevent trainer double-booking during time ranges. |
| **Attendance** | Trainer attendance toggle, save roster, notify absentees | `INSERT` / `UPSERT` into `class_attendance`; `INSERT` into `whatsapp_messages` | One attendance record per student per class session; streak calculation. |
| **Assessment & Grading**| Submit assignment repo, grade submission, submit quiz answers | `INSERT` into `assignment_submissions`, `quiz_attempts`, `quiz_attempt_answers` | Enforce max scores; store frozen answers at submission; update course progress. |
| **Finance & Payments** | Admin invoice generation, student checkout, receipt download | `INSERT` into `invoices`, `payments`, `payment_transactions` | Immutable ledger; gap-tolerant per-brand number sequence (`TAI-2026-000123`). |
| **Certifications** | Benchmark satisfied, issue certificate | `INSERT` into `certificates` | Uniqueness per student per enrolment; immutable verification UUID. |
